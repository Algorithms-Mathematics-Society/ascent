# Reliability and performance audit — 14 September 2026

The changes were verified locally against a production Next.js build and isolated
Firestore/Auth emulators. No real registrations, admin accounts, or emails were
modified, and no deployment was performed.

## Reliability changes

- Reminder addresses are normalized and deduplicated atomically, with the first
  signup timestamp preserved. The per-IP limit is 120 requests/hour to accommodate
  shared campus networks. A synchronous client guard also prevents double clicks.
- Shared rate-limit failure recording now re-reads the counter in a transaction,
  so concurrent requests cannot overwrite one another's updates. Search and admin
  sign-in reserve their request slots atomically before processing.
- Registration receipt, email/phone uniqueness, application, PII, consent and audit
  writes remain in one transaction. Removing an earlier duplicate preflight fixes
  a race where simultaneous retries with one token could receive a duplicate error
  instead of their existing receipt.
- Unlimited registrations no longer write a single global settings counter or
  invalidate public availability on every submission. Public availability reads
  only controls; the admin settings page obtains its count with aggregation.
- Capped registration keeps its atomic counter. Enabling a cap on an unlimited
  window requires closing and saving first. Capacity reductions also recheck the
  latest accepted count inside the settings transaction.
- Each admin page authenticates before starting its data reads. Session lookup is
  memoized within the render request, avoiding repeated verification in layout and
  page. Reminder records remain inaccessible through the public Firestore SDK.
- Public submission and existing admin JSON mutation handlers bound actual streamed
  request bytes, including requests with no Content-Length. Oversized streams are
  cancelled. A page error boundary provides recovery from server failures.

These changes follow Firestore's guidance on [transaction contention](https://firebase.google.com/docs/firestore/transaction-data-contention)
and [avoiding hot documents](https://firebase.google.com/docs/firestore/best-practices),
and Next.js guidance to [authenticate close to data access](https://nextjs.org/docs/app/guides/authentication).

## Checks

- Unit/route tests: 134 passed.
- Firestore rules and rate-limit emulator tests: 18 passed.
- Real transaction concurrency tests: 10 passed. They cover shared-IP reminders, duplicate emails,
  rate-limit bursts, distinct registrations, idempotent retries, competing duplicate
  registrations, exact capacity enforcement, and safe capacity transitions.
- Browser: 30 desktop/mobile checks covering every public/admin page and all three
  legacy registration redirects; eight unauthenticated admin redirects; reminder
  pagination; real local reminder submission followed by visibility in admin.
- Admin page checks used 1,000 synthetic registrations and at least 55 reminders.
- HTTP load test: 200 reminder requests, 40 clients in flight, across 20 simulated
  IP addresses. All 200 returned success. Total 6.28 seconds, median 72 ms,
  95th percentile 3.46 seconds, maximum 6.09 seconds. These include emulator
  transaction contention and are not estimates of production latency. The stricter
  40-request single-IP transaction test completed in 19.1 seconds; shared-IP
  contention remains a latency consideration even though all requests succeeded.
- Production build, TypeScript and lint pass.

## Performance changes

Geist and JetBrains Mono now use locally hosted, preloaded variable WOFF2 files.
The homepage requests roughly 69 KB of fonts rather than 166 KB across six files.
The Garamond display font loads only on the syllabus page, with a size-adjusted
fallback. This removes the measured syllabus layout shift. Decorative graphics
remain deferred; Firebase client code stays off the public registration flow.

Lighthouse also identified invalid definition-list markup in FAQ/admin metrics,
insufficient contrast in syllabus labels, and a missing favicon. Those were fixed.

## Reproducing the checks

```sh
npm test
npm run test:concurrency
npm run test:rules
npm run lint
npm run build
npm start
npx lighthouse@13.4.0 http://localhost:3000 --chrome-flags="--headless" --output=html --output=json --output-path=/tmp/ascent-lighthouse
```

For authenticated page audits, use a local emulator session. Do not place real admin
cookies in reports or run load tests against production without a separate rollout
plan. Concurrency tests refuse to run without a localhost Firestore emulator.

## Scope and remaining operating bounds

These checks establish correct concurrent behavior for the tested workloads; they
do not certify unlimited throughput. Deployed region, Firestore distance/quotas,
serverless cold starts and real devices can change latency. Measure the deployed
site and real-user Core Web Vitals after release. Lighthouse describes a [simulated
mobile laboratory run](https://github.com/GoogleChrome/lighthouse/blob/main/readme.md),
not those production conditions.

The existing registration-review/filter/export and analytics views load at most
2,000 registrations, explicitly show truncation, and process joins in batches. That
bound was not removed by this audit; extending those tools beyond 2,000 records
requires indexed filtering/search and database pagination. Reminder pagination
already uses database cursors and has no equivalent total-list cap. Admin access
management, MFA recovery and external AMS Access synchronization were not subjected
to destructive fault-injection tests.

Rate-limit records have expiry fields; Firestore TTL policies should be verified in
the deployed project. The reminder feature collects requests; it does not send mail.
