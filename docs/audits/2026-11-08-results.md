# Round 1 results review — 8 November 2026

Reviewed result import/validation, request boundaries, caching/concurrency, browser
state and failure recovery, selection correctness, motion lifecycle, image export,
sharing and deployment packaging. No critical defects were found in the reviewed
paths. The following concrete issues were fixed.

| Priority | Finding | Change |
| --- | --- | --- |
| P2 | The client trusted most successful response fields. Missing numeric scores could crash rendering; a rank/selected mismatch could show an incorrect selection. | Validate the full response, problem order/status/scores, rank bounds and exact top-133 selection before rendering. Malformed responses remain retryable. |
| P3 | First lookup performed synchronous disk I/O in the request handler. | Share one asynchronous file-read/parse promise among concurrent cold requests; warm calls use the cached map. Clear a rejected promise so a temporary failure can retry. |
| P3 | Extremely large problem times/attempt counts and a malformed header shape were not rejected at import. | Require safe integer problem counters and the exact header shape; reject malformed exports at build/import time. |
| P3 | The small celebration was clipped to the result header and could scroll away during reveal. | Use a viewport overlay with two particle bursts. Stop after 2.6 seconds, on resize, when hidden, or when reduced motion is requested; cancel animation work and remove listeners. |

## Load test

Ran the production build on a local single Next.js process with Node v24.4.1.
The load generator was on the same machine. Every response was checked against
the authoritative CSV rank and selection, rather than checking HTTP 200 alone.

| Test | Successful | Errors | p50 | p95 | p99 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Before review: 500 simultaneous, warm | 500 | 0 | 238 ms | 367 ms | 388 ms |
| Final build: 1,000 lookups, concurrency 50 | 1,000 | 0 | 40 ms | 74 ms | 102 ms |
| Final build: 500 simultaneous, warm | 500 | 0 | 229 ms | 360 ms | 370 ms |
| Fresh process: 500 simultaneous before any lookup | 500 | 0 | 547 ms | 588 ms | 590 ms |
| Same fresh process after warming: 500 simultaneous | 500 | 0 | 134 ms | 250 ms | 260 ms |

A standalone first lookup took 90 ms in the final run. Result response bodies
averaged 465 bytes. The raw CSV is 72,843 bytes and is read/parsed once per server
instance. There are no database queries, email jobs, outbound API calls, or
per-request file reads in a successful warm lookup. It performs an exact Map
lookup and serializes one small response. Individual responses remain private,
no-store; the landing page and generic social image are built statically.

Process RSS after the tested workloads was approximately 239 MiB in the standard
run and 291 MiB after the larger cold-plus-warm workload. These are whole-process
snapshots including Next.js, V8 and HTTP connections, not per-request allocations
or measurements of the standings map.

The before/after samples do not establish a statistically significant latency
improvement. The cold-I/O change removes blocking work and explicitly coalesces
concurrent imports; the important measured outcome is correct results with zero
failures in the tested bursts. Local results exclude WAN/TLS latency, Vercel
cold provisioning, account limits and production scaling. No production load
test or deployment was performed. The existing Vercel function region is bom1.

Raw measurements: [JSON](2026-11-08-results-performance.json).
Reproduce after building:

```sh
node scripts/benchmark-results.cjs /tmp/results-benchmark.json
node scripts/benchmark-results.cjs /tmp/results-cold.json --cold-burst
```

The script always starts and stops its own local server on port 3111. It cannot
be pointed at the live site. A unit regression also verifies that 500 concurrent
cold callers issue exactly one file read, share the same map, and recover after
read/import failures.

## Browser overhead and sharing

Initial JavaScript gzip bytes from the route/layout build manifest went from
107,044 to 108,454: an increase of 1,410 bytes (about 1.3%). Celebration and sharing
controls are separate chunks loaded only for a selected result. The PNG renderer
is another separate chunk loaded on download. No new packages were installed.

The celebration has 80 particles on narrow screens and at most 120 otherwise.
Its canvas backing buffer is capped at approximately three million pixels
(12 MB), and its animation loop ends after 2.6 seconds. It adds no server work.
Reduced-motion users see the selected result without an animated burst.

The downloadable PNG is 1200 × 627 pixels, generated locally using Canvas with
no screenshot library, network fonts, upload, or server image renderer. It includes
the contest username, rank, participant count, selection and Ascent branding.
Only selected participants see the celebration/share panel. The editable caption
can be copied; denied/unavailable clipboard access falls back to a visible,
selected textarea. LinkedIn opens in a new tab with noopener and only the public
results URL. Participants attach their PNG and review/publish their own post;
the site does not auto-attach an image or post on their behalf.

The generic link-preview PNG is generated at build time (34,320 bytes in the
verified build) and served with immutable cache headers. It contains no participant
data. The image dimensions and manual posting flow follow LinkedIn's
[link-sharing guidance](https://www.linkedin.com/help/linkedin/answer/a525301/sharing-articles-or-links?lang=en).
The static image uses Next's
[Open Graph image convention](https://nextjs.org/docs/app/api-reference/file-conventions/metadata/opengraph-image).

## Final review follow-up

A further review reproduced and fixed these remaining failures:

| Priority | Finding | Fix |
| --- | --- | --- |
| P2 | A structurally valid response for a different username was accepted by the client. | Require the normalized returned username to match the submitted username before revealing a result. A mismatched response leaves the form retryable. |
| P2 | Failure to download an optional sharing or celebration chunk could reach the page error boundary and replace an otherwise valid result. | Catch optional loader failures. Preserve the result and print controls; show a sharing fallback or omit the celebration. |
| P3 | PNG-renderer download failures exposed a technical chunk error. | Show a clear retry/print message. A later click can retry the module download and produce the PNG. |
| P2 (test tooling) | The benchmark exit status ignored errors from its initial cold-burst phase. | Include cold-burst errors in the failure status; also validate the returned username as well as rank and selection. |

The identity and optional-sharing regression checks failed against the prior
production build and pass after the fixes. The new
`test/browser/resultsResilience.cjs` exercises a wrong-user response, blocked
sharing/celebration chunks, and a blocked image-renderer chunk followed by a
successful retry. The ordinary result/selection/share/mobile browser suite also
passes. All 445 unit/route tests and the production build (including type and
lint checks) pass again; CSV deployment tracing and whitespace checks pass.

The benchmark failure path was verified by injecting 500 failed responses only
in the initial cold phase. It exits with status 1 even when all 1,500 subsequent
real local requests succeed. No production requests were used. Earlier latency
figures above remain measurements from the performance pass; the final fixes do
not change the server lookup path. Initial route/layout gzip JavaScript is now
108,557 bytes, 103 bytes above that pass. No new packages or backend calls were
added. No remaining blocking issue was found in the reviewed paths. The original release was pushed as `7939165`. The final cutoff was subsequently
changed to 133 at the organizer's request. Performance figures above remain
historical measurements from the earlier review; the lookup algorithm is unchanged.

contest, and 133 selected for Round 2. These are distinct from the 1,326 rows in
the standings export. Public result cards, share captions, downloadable PNGs,

form-first mobile layout, a more legible staircase panel, clearer AMS Access

before detailed scores. Unselected results use neutral styling and a clear
support path. Narrow-screen artwork and mobile print styles were also checked.

The 445-test suite and production build passed. Browser checks cover 320, 390,
768 and 1024px widths, selection boundaries, sharing, print, reduced motion and
optional-script failures. Desktop/mobile screenshots and the exported PNG were
visually inspected. No new dependencies or backend requests were introduced;
the results route remains approximately 108 kB first-load JavaScript.


## Accounts without submission records

A full production audit of all 1,326 usernames found distinct ranks matching the
CSV, with exactly one response returning 204. Repeated browser checks also
matched the export. The user then supplied participant feedback about accounts
receiving ranks despite not taking the round. The export lists accounts without
submission records, so displaying every listed position as a result was misleading.

The result UI now shows “No submission recorded” with no rank, score summary,
celebration or sharing for entries with no attempts on any problem. It does not
infer that the account holder was absent. Zero-credit submissions still show
results. The internal API retains the original export position; source data and
selection are unchanged.

The export contains 161 accounts with submission records and 1,165 without.
Exactly 133 accounts have at least one accepted solution, and these match the
selected positions 1–133. These are submission counts, not attendance counts;
the export cannot verify claims of 203 or 600+ attendees. Regression checks cover
no-submission accounts around position 204 and submitted solutions with zero credit.
